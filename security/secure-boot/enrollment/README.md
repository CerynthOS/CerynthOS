# Key enrollment procedure

Enrollment is a security-critical firmware operation. This document defines the
procedure; it does not perform enrollment.

## Prerequisites

- Physical or virtual machine with UEFI firmware supporting Secure Boot.
- Authorized operator with firmware setup access.
- Public certificates for PK, KEK, db, and dbx (never private keys).
- `efitools` (`efi-updatevar`, `efi-readvar`, `openssl`) for variable updates.

## Enrollment order

1. **Read current state**: `efi-readvar` to capture existing PK/KEK/db/dbx.
2. **Enter Setup Mode**: clear PK via firmware setup (this disables Secure
   Boot enforcement until a new PK is enrolled).
3. **Enroll dbx** (revocations first): `efi-updatevar -f dbx.esl dbx`.
4. **Enroll db** (allowed signatures): `efi-updatevar -f db.esl db`.
5. **Enroll KEK** (signs db updates): `efi-updatevar -f KEK.esl KEK`.
6. **Enroll PK last** (root of trust): `efi-updatevar -f PK.esl PK`.
   Enrolling PK re-enables Secure Boot enforcement.

## Recovery if a key is lost or compromised

1. Enter Setup Mode (firmware physical presence required).
2. Enroll a new PK and KEK generated by the authorized key store.
3. Re-enroll db and dbx signed by the new KEK.
4. Re-sign the bootloader and kernel with the new db key.
5. Verify that the old key no longer boots the machine.

## Revocation

Revocation is performed by appending the old certificate's signature to `dbx`
and enrolling the updated `dbx` via `efi-updatevar -f dbx.esl dbx`. A revoked
key cannot authorize future boots. Existing signed binaries must be re-signed
with a non-revoked key before the revocation is enrolled.

## QEMU / OVMF test environment

For development, create an OVMF variable store with test keys using
`tools/efitools` or `qemu-system-x86_64` with a fresh OVMF_VARS.fd. The test
keys generated by `scripts/generate-test-keys.sh` are suitable for this
isolated environment only.

## Validation cases

| Case | Expected result |
|------|-----------------|
| Correctly signed kernel | Boots |
| Unsigned kernel | Rejected by firmware |
| Kernel signed by unauthorized key | Rejected by firmware |
| Revoked signing key | Rejected by firmware |
| Invalid update | Previous boot entry remains intact |

These cases require a live OVMF/UEFI environment to execute. This repository
does not claim they have been run.
